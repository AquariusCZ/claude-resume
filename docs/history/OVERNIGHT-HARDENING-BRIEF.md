# 过夜加固任务书(目标模式,无人值守)

冻结于 2026-08-06。**执行者是另一个 AI,整夜无人值守,早上交付。**

目标只有一个:**让这个程序足够稳**。不是加功能,不是重构得更漂亮——是把
「已经写下来的红线」变成「有测试钉住的事实」,并把藏着的脆弱点翻出来。

---

## 0. 你必须先知道的三件事

**第一,这个项目的测试是事故的化石记录。**
仓库里每一条看起来啰嗦的断言背后,通常都有一次真实事故。举例:曾经一个测试
resume 了真实会话,AI 带着旧上下文执行并 push 了 commit;曾经 mock 猜错了
`im.image.create` 的返回结构,测试全绿而线上静默失效;曾经生成器写出的 TOML
形状是我们自己臆想的,从没拿真的解析器跑过,错了三个月才暴露。

**所以:绝对不许通过弱化断言、放宽期望值、删测试、加 `[Skip]` 来让红变绿。**
测试红了,要么是实现真错了(改实现),要么是测试写错了(改测试并说明为什么原来的
期望是错的)。分不清是哪种,就**保留红的状态并记录**,别猜。这一条违反即整夜作废。

**第二,生产正在跑。**
`cc-connect.exe` 此刻是本机**唯一**的飞书事件消费者,用户白天要用它。
飞书长连接是集群模式——同一个应用起两个消费者,事件会被随机投递给其中一个,
表现为「机器人时灵时不灵」。这个坑本项目已经踩过一次。

**第三,部分完成是可接受的,半成品不是。**
阶段按价值排序。跑到哪算哪,但**每个阶段必须独立 commit**,不许攒一个大提交。
早上我要能对任意一个 commit 单独 review 和 revert。

### P0 — 基线固化(时间盒 30 分钟)

1. 跑一次全量测试,记录数字。**如果基线本来就不是 443 全绿,立刻停手并报告**——

2. 确认 `cc-connect.exe` 恰好 1 个进程,记下 PID 和启动时间。**整夜结束时再确认一次

3. `git status --short` 必须干净。
4. 记录 `~/.cc-connect/config.toml` 的 **SHA256**(不要读内容)。结束时再算一次,
   必须一致。

**DoD**:一份基线快照(测试数、cc-connect PID、config SHA256、git HEAD)。

### P1 — 启动长跑浸泡(时间盒 20 分钟启动,之后整夜后台运行)

**先启动它,再去做 P2**——它要占整夜墙钟,别放到最后。

在**完全隔离的环境**里拉起一个 Worker 宿主:

- `AIRESUME_TEST_PIPE_SUFFIX` = 你生成的随机后缀;
- shadow root 指向系统 temp 下的新建目录,**不是** `%LOCALAPPDATA%\ClaudeResumeShadow`;
- 该目录里的产品配置必须 `enabled: false`、`armed: false`、`continuous: false`
  ——浸泡测的是常驻开销,不是让它真去续跑;
- 每 5 分钟采样一次:句柄数、线程数、私有字节、GC 堆大小,写进
  `docs/evidence/soak-<日期>.csv`;
- 每 5 分钟经 IPC 发一次 status 请求,确认管道层没有累积泄漏。

**判据**:采样点 ≥ 60 个(约 5 小时)时,句柄数与私有字节**不得单调上升**。
允许波动,不允许持续爬升。

**诚实性要求**:空转浸泡只能证明「空闲不泄漏」。报告里**不许**把它说成
「长时间稳定运行已验证」。如实写清楚测了什么、没测什么。

**DoD**:CSV 证据 + 一段结论(有/无增长趋势,依据是哪几列)。

### P2 — 红线覆盖审计与补测(时间盒 3 小时,**本夜最高价值项**)

`CLAUDE.md` 的「测试红线」「会话生命周期」「安全约束」「GUI 服务状态语义」四节
写满了真实事故。任务:**逐条对照现有 443 个用例,找出没有测试钉住的红线,补上。**

方法:

1. 先把四节里的每一条**可判定的断言**抽成一张表(条目 → 出处行 → 语义);
2. 对每条,在 `csharp/test/AiResume.Tests/` 里找对应用例(grep 类型名、方法名、
   断言特征);
3. 判定三档:**已覆盖** / **部分覆盖(缺哪个分支)** / **完全没测**;
4. 对「完全没测」和「部分覆盖」,按下面的优先级补测试。

**优先补这些**(它们对应的是已经发生过的事故,不是假想):

- **RunContract 错误分类**:只有结构化 HTTP 408/504/`gateway_timeout` 才是
  `failed_provider` 超时;DNS/TCP/TLS/connection reset、进程消失、监控自身异常
  一律 `failed_local`;用户停止是 `cancelled` 且**不得触发 fallback**。
  每种输入至少一个用例,尤其是「本地故障被误判成 provider 故障然后换线重放」这条
  ——它一旦发生就是重复执行用户的任务。
- **无总时限**:chat/query/modify/resume/probe 五种任务都不得存在客户端总时限。
  写一个用例证明「静默 N 分钟不产生失败」,并证明 `heartbeatAt`/`lastOutputAt`/
  `silentSeconds` 只进指标不进判定。
- **子进程登记表的回收判据**:必须**父 agent PID + 子 PID + 5 秒内启动时间 +
  provider 命令签名四项全匹配**才允许回收。补反例用例:PID 被系统复用给了别的进程
  (同 PID、启动时间差很远)时**绝不能杀**。
- **CIM 探测三态**:found / gone / failed 必须区分,**只有明确 gone 才能删登记**;
  failed(查询本身出错)时必须保留登记并重试。
- **config 写入并发**:`ProductConfigStore.Update` 是锁内读-改-写。补一个多线程/多进程
  并发用例,证明两个写者各自只改自己负责的字段、互不覆盖。这条对应的事故是
  「锁外读旧快照后整体写回」。
- **原子写**:临时文件 + fsync + 替换。补用例:替换前崩溃 → 旧文件完整可读;
  临时文件残留 `.tmp-*` 且内容完整时,应作为恢复候选而不是垃圾。
- **会话生命周期**:14 天归档 / 30 天删除只对闲聊与只读查询生效,
  **项目工作会话绝不自动归档或删除**。补一个「工作会话放置 60 天仍在」的用例。
- **授权边界**:非 owner 的查询/闲聊必须禁全部文件工具(plan 模式拦不住"读")。
  补用例证明工具集在非 owner 路径下确实为空,而不是靠模式约束。

**红线**:补测试时若发现实现真的有 bug,**修实现**并在提交信息里单独点名;
若你无法判断是实现错还是理解错,**保留失败的测试、标注原因、继续下一条**,
不要为了绿而改任何一边。

**DoD**:① 覆盖矩阵表(写进 `docs/RED-LINE-COVERAGE.md`);② 新增用例全绿;
③ 一份「发现但未修的疑似缺陷」清单。

### P3 — 故障注入(时间盒 2.5 小时)

现有 `PowerLossRecoveryTests.cs` 是起点,扩展它。目标是回答:
**状态文件在各种"写到一半"的形态下,程序是安全失败还是静默错误?**

对每一个持久化状态文件(run store、项目索引、事件队列、登记表、产品配置),
构造这些形态并断言行为:

| 形态 | 期望 |
|---|---|
| 文件为空(0 字节) | 视同不存在,不得抛未捕获异常 |
| JSON 被截断在中间 | 拒绝加载并保留原文件,不得静默当成空 |
| 合法 JSON 但字段缺失/类型不对 | 明确拒绝,不得默认成危险值(如 `armed=true`) |
| UTF-8 BOM / CRLF 混排 | 正常解析 |
| 只读文件 / 目录不可写 | 明确报错,不得吞掉 |
| `.tmp-*` 残留且内容完整 | 作为恢复候选 |
| `.tmp-*` 残留但内容截断 | 丢弃,不得当成恢复候选 |

**特别注意「不得默认成危险值」**:一个损坏的配置被解析成 `armed=true` /
`skipPermissions=true` / `allowFrom=""`(等于放行所有人),比直接崩溃危险得多。
每个安全相关的布尔与名单字段都要有一条「损坏输入 → fail-closed」的用例。

**DoD**:新增故障注入用例全绿 + 一份「哪些字段目前不是 fail-closed」的清单。

## 4. 卡住了怎么办

**不要硬闯。** 时间盒到了就收,把没做完的写进晨报。

具体规则:
- 同一个测试连续修 3 次仍红 → 保留红的状态,记录你的两种假设,进下一条;
- 需要重启生产进程才能验证的 → **跳过**,记进「需要人工执行」;
- 需要在飞书里发消息才能验证的 → **跳过**,只有 owner 能做;
- 需要改变产品行为、架构、依赖或数据兼容性的 → **停手**,写成方案选项进晨报,
  不要自行决定;
- 发现任务书本身和现场对不上 → 以现场为准,并在晨报里点明任务书哪里错了。

## 5. 晨报格式(必须包含「我没做到什么」)

写进 `docs/OVERNIGHT-REPORT-<日期>.md` 并 commit:

1. **一句话结论**:程序比昨晚更稳了吗,依据是什么;
2. **阶段表**:每阶段 完成/部分/未开始 + 提交 sha + 证据位置;
3. **测试数变化**:443 → N,新增用例分别钉住了哪条红线;
4. **发现的缺陷**:分「已修」「已确认但未修」「疑似,需人工判断」三档,
   每条给出复现路径;
5. **我没做到什么**:时间盒截断的、跳过的、无法验证的——**这一节写得越诚实越有用**。
   过夜任务最常见的失败模式是「报告说全做完了,实际有一半没验证」;
6. **不变量核对**:cc-connect PID 前后一致?config.toml SHA256 前后一致?
   git status 干净?有没有碰过红线清单里的任何一项?
7. **给人的下一步建议**:按「必须做 / 建议做 / 可选」三档。

## 6. 为什么是这些活(设计依据,供你判断优先级用)

这个程序此刻的不稳定,不在「功能没写完」,而在三处:

- **写下来的红线没有全部被测试钉住**。红线是事故记录,没测的红线等于随时会复发的事故。
  → P2。
- **状态文件的损坏形态没有系统性覆盖**。这个程序的核心价值是「崩了还能接着跑」,
  而崩溃恰恰最容易在写到一半时发生。一个损坏配置被解析成 `armed=true` 比崩溃危险。
  → P3。
- **常驻开销无人观测**。它要 7×24 跑在用户机器上,句柄或内存单调上升就是定时炸弹。
  → P1。

P4/P5 优先级更低,因为它们改善的是**人的判断质量**,不是程序本身的稳定性。
时间不够就砍它们,不要砍 P2/P3。
