### Target run lifecycle (not deployed)

ADR-0002 replaces the target's earlier deadline-oriented task model with durable Start/Status/Cancel. The C# Worker will own `TaskOrchestrator`, `ProcessSupervisor`, `ProviderAdapter`, `RunStore`, `HealthProbe` and `Transport`; GUI, Feishu and cc-connect adapters consume one RunSnapshot/event stream. All target AI generation and health probes have no client total-duration timer. The Worker observes persisted state and process liveness every 15-30 seconds; `heartbeatAt`, `lastOutputAt` and `silentSeconds` remain metrics only. Structured HTTP 408/504/`gateway_timeout` is `failed_provider`; DNS/TCP/TLS/reset, process disappearance and monitoring/storage failures are `failed_local`; user stop is `cancelled`. Automatic fallback requires a structured provider failure, no side effects and a fully closed prior child. The current Node query/chat 30-minute deadline and provider-probe wall budget documented below remain current behavior until the corresponding migration stage passes.

```
┌─────────────────────────┐        writes         ┌──────────────────┐
│  picker.ps1 (WPF GUI)   │ ───── config.json ──► │  config.json     │
│  - discover projects    │                       │  state.json      │
│  - arm / disarm         │ ◄──── reads log ───── │  logs/run-*.log  │
│  - live monitor         │                       └────────▲─────────┘
└─────────────────────────┘                                │ reads/writes
            ▲ launched by launcher.vbs (hidden)            │
            │                                     ┌─────────┴─────────┐
      Desktop shortcut                            │  checker.ps1      │  ◄── Scheduled Task
                                                  │  (the engine)     │      every 2 min
                                                  └─────────┬─────────┘
                                                            │ uses
                                                  ┌─────────┴─────────┐
                                                  │  lib.ps1 (shared) │
                                                  └───────────────────┘
```

**Why split?** The resume run can take many minutes/hours. If it ran inside the WPF UI thread the window would freeze and the Stop/Disarm controls would die exactly when needed. So the GUI only *configures and monitors*; the actual waiting + resuming happens in a separate process owned by a **Scheduled Task**. That also makes it survive closing the window / logging off-and-on / reboot.

## The checker state machine (every ~2 min) — probe-driven, fixed cadence

There is **no reset-time estimation**. The checker does not fire on a clock; it fires when a **live probe** proves the account is usable again, and it probes on a **fixed interval** (not gated by any estimate — an off estimate used to delay limit-detection):

1. Recover any registered background child from `checker-ai-child.json`; if ownership/termination cannot be confirmed, fail closed. Then capture the current `armCycleId`. If disarmed → return. If no projects selected → return.
2. Throttle: probe every `probeIntervalMinutes` while usable (GUI chip: 5/15/30, default 15), tightening to ~4 min once limited. If the last probe was more recent than that, return.
3. **Probe** (`claude -p "ready" --max-turns 1`, cheap model):
   - **limited** → set `sawLimited=true`, stay `waiting`.
   - **not ready** (network/other) → `waiting`, retry — **fail-closed**, never fire on an ambiguous read.
   - **usable + never saw limited** → you armed *before* hitting the cap; **stay armed** and keep watching (an earlier version auto-disarmed here, which silently cancelled exactly the "arm right before the limit, go to bed" flow).
   - **usable + had been limited** → the reset happened → **FIRE**.
5. **Fire**: resume selected projects **sequentially**. Per project: verify the cycle → git dirty-guard → verify again → persist a `launching` intent → spawn `claude --continue` → upgrade the record with parent/child PID, cycle run key, project and verified start time → record cycle-bound status. If disarmed or replaced, verified `taskkill /T /F` stops the process tree. A crash between intent and PID registration is recovered by parent PID + launch-time window + command signature.
6. **One-shot**: after a successful run, atomically read the latest config and set `enabled=false` only if the same cycle is still current. Rapid disarm/re-arm creates a new cycle, so the old checker cannot overwrite the new config or state. The Scheduled Task has `ExecutionTimeLimit=PT0S`; Windows' default 72-hour limit is never allowed to become the real cutoff.

### Why probe-driven, no estimation?

Every local estimate we tried (ccusage's gap-split blocks; a rolling-5h-window over `~/.claude` timestamps) could be off by hours from Claude's real rolling session window (observed: one estimate said **4h35m** when claude.ai said **1h12m**). Worse, when the estimate *gated probing*, an over-long estimate delayed limit-detection by exactly its error. So estimation was removed entirely: the checker probes on a fixed interval and **fires only on a live probe**, which is correct regardless.

### Reading the **exact** reset + utilization live

The probe (`Test-ClaudeReady`) runs `claude -p "ready" --max-turns 1` as `--output-format stream-json --verbose`. Claude emits a `rate_limit_event` line carrying the server's authoritative values — the same numbers the interactive `/usage` screen shows:

```json
{"type":"rate_limit_event","rate_limit_info":{"status":"allowed_warning","resetsAt":1783706400,"rateLimitType":"five_hour|seven_day","utilization":0.88,...}}
```

`Test-ClaudeReady` parses `resetsAt` (Unix seconds) and `utilization` per `rateLimitType` (both `five_hour` and `seven_day`); `Save-RealResetFromProbe` caches the reset in `state.json` **as an integer** (ConvertFrom-Json rebases ISO strings to local `[DateTime]` but leaves integers untouched → timezone-safe). The GUI chip shows **both windows** (`5h 62% · 7d 53%`), each switching to a precise countdown (`5h 限流 · 1h 04m`) once limited. Note the server only sends a window's `rate_limit_info` once it is **utilized enough** (and always when `blocked`), so early in a fresh 5h window the server sends no 5h number — the chip shows `5h 低` for that window (well below its limit) alongside the 7-day figure. `/usage` itself is interactive-only (no `claude usage` subcommand), so this stream-json event is the scriptable way to read the same data.

### The GUI workbench

`picker.ps1` is a dense operational workbench rather than a settings picker: projects occupy the main scan area; the right rail exposes the current AI, live provider state, Claude quota, probe interval and arm controls; logs remain visible below. Clicking **当前 AI** opens a provider-grouped selector; only providers whose latest real request succeeded expose model items, while unavailable provider configuration fields remain visible so credentials can be repaired. **会话** opens a virtualized table with project/user/AI/state/last-use/size columns and confirmed archive/restore/delete actions.

The GUI probes every provider **once when it opens** and again when **立即刷新** is clicked — never on a GUI timer. Claude uses `Test-ClaudeReady`; OpenAI and DeepSeek use `provider-health.js`, which sends concurrent, minimal no-tool requests through the same production runners as Feishu. Key presence or command discovery only determines whether a provider can be probed; it never produces a green state. The synchronized result distinguishes checking, available, unconfigured/missing, authentication, billing/quota, network/timeout and model failures. Claude probe failure also drives the quota chip, so a failed login can never fall back to “空闲”. Screenshot and GUI self-test modes intentionally stay offline and render **待检测**.

All slow probes run on a background runspace so the window never freezes; results land in a synchronized hashtable the 1-second UI timer reads. The GUI is **single-instance** (a named `Mutex`; a second launch focuses the existing window via its process `MainWindowHandle`) and uses the same versioned multi-resolution orange `AR` icon for the WPF window, taskbar and Desktop shortcut. The installer validates the saved shortcut icon instead of silently accepting the Windows script fallback. Custom button templates include keyboard focus states; destructive session/log actions require confirmation.

## Key implementation details (and the bugs they avoid)

- **Timezone (the ~8h footgun).** `ConvertFrom-Json` silently rebases ISO-`Z` datetimes to local (+08:00 here). We sidestep it entirely by storing the reset as a **Unix integer** (`resetsAt`) — integers round-trip through JSON untouched — and reading it back with `FromUnixTimeSeconds`, compared against `[DateTimeOffset]::UtcNow`. Verified in both PowerShell 5.1 and 7.
- **Launching `claude`.** `Start-Process claude.cmd -RedirectStandardOutput` can't exec a `.cmd` (UseShellExecute=false). We launch `cmd.exe /c claude.cmd …`, **tail the redirect file** for live log lines, and kill the **whole process tree** (recursive `Win32_Process` by `ParentProcessId`) on stop/timeout — the returned PID is only the cmd wrapper. Verified with a stand-in that spawns children.
- **`$p.ExitCode` is a lie in PS 5.1 (the bug that silently blocked every resume).** After `Start-Process -PassThru`, `.ExitCode` reads **`$null`** once the process has exited — with `WaitForExit(ms)` *and* with `HasExited` polling (both verified live; `WaitForExit(ms)` opens the handle SYNCHRONIZE-only). Result: a *successful* probe fell through to the exit-code test, read `$null ≠ 0`, logged `探测未就绪 (exit-)`, and the fail-closed loop never fired. Fix, twice over: `$null = $p.Handle` right after launch caches a query-capable handle, **and** success no longer relies on the exit code at all — the stream-json line `"type":"result" … "is_error":false` is the authoritative success signal (checked before the fuzzy limit-text match, so a successful run that merely *mentions* limits can't be misread as limited; the structured `"status":"blocked"` check still runs first).
- **Probe self-noise.** Probes run with `-WorkingDirectory` = AppDir so their own `claude` sessions land in one known `.claude/projects` folder that project discovery skips — they never pollute the project list.
- **Project discovery.** The `~/.claude/projects/<encoded>` folder names are lossy/ambiguous, so we read the real `cwd` (and last-used time) from each session `*.jsonl`. Resume uses `claude --continue` in that `cwd` (continue the most recent conversation there) — which also works for folders added via **+ 文件夹**.
- **Encoding.** Every `.ps1` is saved **UTF-8 with BOM** so Windows PowerShell 5.1 parses non-ASCII correctly.
- **Responsive UI.** The GUI's 1-second timer only does fast local/file reads (log tail, config/state, countdown from the cached probe result); the slow work — the on-demand probe — runs on a background runspace and publishes into a synchronized hashtable. Button actions show a 6-second "flash" status so the timer doesn't stomp their feedback.
- **Availability is an observed fact, not configuration metadata.** A configured API key can be expired and an installed Claude CLI can be logged out. Provider rows become green only after a real request succeeds; all failure classes remain visible and the manual refresh rechecks all three providers. This rule is covered by `test/ai-providers.js`, the PowerShell GUI self-test and live provider smoke tests.
- **AV-safe.** Nothing uses the `.lnk → powershell -WindowStyle Hidden -ExecutionPolicy Bypass` pattern that Huorong (火绒) deletes; launches go through `wscript`-hidden `.vbs` and the Scheduled Task.

## Feishu integration (one app bot: notify + two-way)

### Multi-provider execution

Each Feishu user selects an AI profile independently. The built-in profiles are OpenAI GPT-5.6 Sol, DeepSeek V4/V4 Pro, and Claude default/Fable/Opus/Sonnet/Haiku. GPT-5.6 Sol and DeepSeek V4 Pro are available to viewers as well as owners; Fable 5 remains owner-only. Selection is provider-health-gated: the agent probes OpenAI, DeepSeek and Claude on boot, refreshes a snapshot older than five minutes when the model picker opens or a formal OpenAI/DeepSeek run needs a stale route, and exposes only providers whose real request succeeded. OpenAI/DeepSeek probes remove inherited proxy variables case-insensitively for the first direct attempt. Only a `transient` result may use the configured child-only proxy as a second attempt; auth, quota, model and local-command failures are terminal for route selection. When a fallback proxy exists, the 60-second wall budget is weighted up to 45 seconds to direct and 15 seconds to proxy; each attempt reserves the runner's termination grace and the second receives only the remaining deadline. If the direct child has not confirmed close after termination grace, the probe stops without launching the proxy. A `childPending` snapshot blocks every re-probe regardless of negative-cache age; runner `waitForIdle` removes its temp directory after the real close and immediately expires that snapshot. The snapshot stores `route=direct|proxy` plus a hash of the relevant key/endpoint/proxy configuration. Successful routes have a five-minute TTL, failures have a 30-second negative TTL, and a fingerprint mismatch invalidates either immediately. GUI/Feishu status text reports the successful route. `aiProxy` is not applied to Claude. Provider availability gates that provider's registered models; old card values and `模型 xxx` text commands are checked against the same snapshot. The DeepSeek display profiles map to `deepseek-v4-flash[1m]` (V4, effort `high`) and `deepseek-v4-pro[1m]` (V4 Pro, effort `max`); `deepseekMillionContext=false` removes the `[1m]` suffix, and `deepseekEffort` can override the default effort.

In the migration worktree, `runForUser` is a thin wrapper over `task-orchestrator.js`; that boundary performs current-compatible admission, candidate/fallback and health-preflight cancellation, then calls `ai/agent-adapter.js` for one unchanged attempt, which delegates to `ai/runners.js`. Production continues using the previously deployed direct runner path until an authorized deployment. OpenAI runs through `codex exec --json`. New and resumed Codex invocations are built by one `buildCodexArgs` function: provider/model/reasoning/tool policy and the non-Git scratch-directory invariant `--skip-git-repo-check` are shared, while only the CLI grammar (`exec` vs `exec resume`, `-C` vs native thread id) differs. This prevents mode-specific option drift. Each invocation explicitly defines a minimal custom Responses provider from `openaiBaseUrl`, reads its bearer token from a child-only environment variable, and applies `openaiReasoning` (`xhigh` by default). This remains valid even for non-owner runs using `--ignore-user-config`, so security isolation cannot silently redirect the request to the built-in OpenAI endpoint. Claude runs through Claude Code stream-json; DeepSeek also runs through Claude Code but receives child-only official Anthropic-compatible endpoint/model/token environment variables. For OpenAI/DeepSeek, the orchestrator consumes the fresh health snapshot's route and fixes that route in the child environment. Waiting on the shared route probe has a task-keyed cancellation gate and participates in the current Node task's absolute legacy deadline; cancellation or deadline exhaustion returns before any formal child is spawned. This deadline is compatibility behavior, not the target RunContract. A formal task is never replayed merely to switch direct/proxy because a timeout may be ambiguous; a later task can refresh the route after the snapshot expires. Provider fallback remains separate: retryable auth, rate-limit, unavailable-model and transient network errors may move to the configured fallback profile only when no side effects were observed and the previous child has confirmed close. The migration-only D-002 parser marks malformed JSON, unknown/invalid Claude tool/content activity and unknown/invalid Codex item activity as side effects; the flag is monotonic, so a recorded retryable 429 after ambiguous activity cannot start a second provider. Explicitly known read-only text/thinking/search/read events remain unmarked. This hardening is not yet deployed, and Stage 4/6 must prove the same contract in the target orchestration path.

Sessions are provider-native. Claude/DeepSeek use Claude Code JSONL sessions; OpenAI lists and resumes Codex threads through app-server/`codex exec resume`. Chat and query memory are keyed by user and profile; query memory also includes the project path. Their isolated cwd is intentionally not a Git repository, so both first-turn and resume commands must carry the shared Git-check bypass. Switching provider therefore creates/resumes a compatible session instead of passing one provider's id to another. Successful turns rewrite the scratch marker with `kind`, `openId`, `profileId`, `engine` and `updatedAt`.

### Session lifecycle

`session-manager.js` is the only deletion/archive authority used by both the GUI and agent. Every 6 hours (and 10 seconds after agent startup), it applies these defaults from `config.json`:

- Feishu chat/query inactive for 14 days: archive and remove the active marker/cwd.
- Feishu chat/query inactive for 30 days: permanently delete, measured from `lastUsedAt`, not archive time.
- Project work sessions: never auto-archive or auto-delete.
- Safe tool garbage: old AppDir quota probes, Windows/system sessions and known temporary provider/test sessions are deleted with matching artifact directories.

Claude archive entries move both `<sessionId>.jsonl` and the sibling `<sessionId>/` artifact tree under `session-archive/<archiveId>/claude/`, preserving relative paths for restore. Codex uses app-server `thread/archive`, `thread/unarchive` and `thread/delete`. `session-archive.json` stores the display metadata, original marker snapshot and restore payload. A restored scratch marker gets a fresh `updatedAt` so it is not immediately re-archived.

**One bot does both.** With a self-built app configured, notifications and two-way commands both go through the single app bot, in the same chat. `Send-FeishuNotify` (in `lib.ps1`) prefers the **app API** (`im/v1/messages` with a cached `tenant_access_token`) sending to `feishuChatId` — the **owner's** p2p chat. Only a p2p message from someone explicitly in `feishuAuthOpenIds` may (re)bind it (bootstrap: while unlocked and unset, the first p2p message binds) — a coworker's or group message can never hijack the notification channel. Every notification line carries a local `HH:mm` stamp. If the app isn't fully set up it falls back to a **custom-bot webhook** (optionally **签名校验**-signed: HMAC-SHA256 with key `"<timestamp>\n<secret>"` over an empty message, base64, as `{timestamp, sign}`).

### Local editor completion bridge

`install.ps1` installs three user-level adapters: Codex `notify` (CLI/Desktop/VS Code share the same config), Claude Code `Stop` (CLI and VS Code share user settings), and Cline global `TaskComplete.ps1`. Install is idempotent and preserves the pre-existing chain in each client. Codex's Desktop computer-use wrapper remains at the top and receives an AI Resume handler as its nested `--previous-notify`; an existing multiline/non-JSON-compatible TOML value or `.cmd`/`.bat` notifier is rejected without rewriting the config because it cannot be chained safely. Claude keeps unrelated hooks and uses the schema's direct `command` + `args` form rather than a Windows shell; Cline's previous TaskComplete script stays beside the managed wrapper so `$PSScriptRoot` remains valid, runs first, and suppresses the notification when it returns `cancel:true`.

Each adapter only normalizes the client payload and atomically writes a small JSON file under `completion-events/`; it does not read project files or hold Feishu credentials. Codex admission is stricter than event-ID de-duplication: the thread id and rollout `session_meta` id must match under `CODEX_HOME`; missing/ephemeral turns and persisted metadata marked by `parent_thread_id`, `thread_source=subagent`, or `source.subagent` are rejected, while a user-created top-level fork with only `forked_from_id` remains eligible. Every remaining root must be outside Desktop's generated `Documents\Codex\<date>\<slug>` projectless tree unless an explicit Git boundary exists there. A root Codex task therefore produces one meaningful project notice instead of additional internal-turn notices or an opaque `wo-x` project label. Queue-write and admission failures write credential-free local-time diagnostics. The Stage 1 compatibility runtime claims at most 20 files per sweep, rejects invalid/oversized/older-than-seven-day events, rejects UNC/device paths before filesystem access, derives the displayed client from the controlled source enum, resolves the project from the event's local cwd/workspace and nearest Git root, sends only project/client/local-time metadata to `feishuChatId`, then persists a bounded seven-day de-duplication map. The Feishu create request uses a deterministic UUID derived from the event ID, so a crash between send and local acknowledgement can retry without duplicating the remote message. Failed sends restore the queue file. Missing `feishuChatId` leaves it queued; `completionNotifyEnabled=false` discards queued events without sending.

Project resolution never reads or hard-codes the GUI's project count. A known project name is used when the path matches discovery/custom configuration; otherwise the basename of the real Git/workspace root is used. `AI_RESUME_INTERNAL_RUN=1` is injected into every Node runner child and PowerShell engine process, preventing provider probes, Feishu work and background resume from recursively notifying the owner.

The supported boundaries are Codex turn completion, Claude Code Stop and Cline TaskComplete. Codex/Claude notifications deliberately say the current response ended rather than claiming the whole long-lived conversation closed; Cline uses its true task-completion boundary after any earlier hook permits completion. `DeepSeek V4 for Copilot Chat` is excluded: its `LanguageModelChatProvider` observes each model API response/`finish_reason`, while VS Code exposes no public observer for completion of the enclosing Copilot Agent task. A fork would therefore be both semantically unreliable and maintenance-heavy. DeepSeek remains covered when it runs inside Claude Code or Cline.

The **two-way agent** enters through `feishu-agent.js` and currently executes the Node compatibility shell in `feishu-runtime.js`. That shell uses the official `@larksuiteoapi/node-sdk` `WSClient` — a persistent WebSocket to Feishu, so **no public IP** is needed. It registers `im.message.receive_v1`(+`_v2`), `card.action.trigger` (button clicks) and `application.bot.menu_v6` (the persistent bottom menu), and runs a small **conversation state machine**, keyed by chat in `feishu-sessions.json` as `{mode, project, sub, work, workProfile, workTitle}`. `work` is always a provider-native session id; `workProfile` prevents a Codex thread id from being resumed by Claude Code or vice versa.

**Per-user routing.** Every user talks to the bot in **their own** p2p chat. `feishu-userchats.json` maps open_id → that user's chat, learned **only from p2p messages** (a group @-mention must not poison it); bottom-menu events carry no chat_id, so replies route via this map, falling back to sending by open_id (`od:` targets). A menu-first user's state under the `od:` pseudo-key migrates to the real chat on their first message. **Immediate-ACK, ordered dispatch**: the WS layer ACKs an event only after the registered callback resolves, so `dispatchEvent` returns immediately but queues handlers by chat. Different chats still run concurrently; the same chat preserves arrival order, which is required for destructive state transitions such as `忘记查询` followed immediately by a new query. Long AI work leaves that short event queue through `bg()` — an awaited 4-minute run used to block the ACK and made the whole bot look dead.

### Conversation state machine (two shallow levels)

- **idle** (default): does **nothing** until you pick something — a plain message just shows the menu card. This prevents accidental quota spend / edits.
- **chat**: talk to the selected AI in a user + profile scratch session (`feishu-chat/`, kept out of project discovery) — touches **no project**. Owners keep the provider's normal tool surface; non-owners get no file/exec tools.
- **project**: entering a project shows a **project sub-menu card** where you first pick **👁 只读查询** or **✏️ 修改项目** (`sub`), then just type. (A viewer skips the choice — they go straight to a query-only card.)
  - **✏️ modify** → a provider-aware **session picker**: the project's 5 most recent Codex threads or Claude Code JSONL sessions, plus 🆕 新开会话. Enumeration runs in `bg()` with an `AbortController`; the card callback does not wait for Codex app-server, local JSONL I/O, or Feishu network I/O. A read that outlives 250ms patches the **same serialized control card** to a loading state; fast reads cancel that timer before the final picker is enqueued. If the clicked card was deleted, the loading fallback records its replacement message id and the final picker follows that same card instead of creating a duplicate. Each picker gets a random token bound to **chat + project hash + profile**. Project/model/page changes invalidate the token and abort the old Codex child, so a late result or an old card can never attach project A's session to project B. Provider errors remain distinct from an empty history and render retry/new-session choices. Picking one reads a digest of its last 2 turns, then sends it only if **project + session id + profile** still match; switching state during the read discards the stale digest. Every later message continues **that provider-native session**. A new Claude/DeepSeek session gets a UUID up front; Codex stores `work="new"` until the first successful run returns its thread id. Nothing runs until a session is picked — it never guesses.
  - **👁 query** → read-only (`--permission-mode plan`) in **your own** per-(project, user) query session (see below). Viewers are always forced here; a full user opts in per-message with the 查询/只读 prefix or by picking the mode.

**Commands are mode-scoped**: fuzzy forms (bare project name/number, greetings, **进入 `<编号|名字>`**, **`<项目名> <指令>`** one-offs) parse **only in idle**. Explicit commands work in every mode. AI profiles are stored in `feishuChatProfile` / `feishuUserProfiles`; the old model fields are compatibility mirrors. Text aliases include `模型 sol`, `模型 v4`, `模型 v4pro`, `模型 claude`, and Claude family names, but a parsed profile is not saved unless its provider is currently health-available.

### Cards: one control card, updated in place

`buildMenuCard` (main) and `buildProjectCard` (sub-menu) are the two forms of a **single control card** tracked by `lastCard[chatId]`, rendered **role-aware** (viewers see only what they can use). The main card shows one **选择可用 AI** command instead of flattening every model into the project menu. `buildModelCard` is a two-level provider → model flow: provider parent buttons are health-filtered, model child buttons remain role-filtered, and an in-progress refresh exposes no selectable values. Every control-card transition goes through `enqueueControlCard`: writes are serialized per chat, resolve their target from the live card at execution time (including the window while a failed patch is creating its replacement), patch it when possible, and create one visible replacement if the live card was pushed up, deleted, failed, or timed out. `controlCardEpoch` advances whenever user input or ordinary text/result/model messages push navigation upward; an older patch cannot cross that visibility epoch and re-register an off-screen card. Project-card actions carry a project hash, while picker actions add a random profile-bound token; accepted picker actions are consumed once so a real double click cannot replace the restored project card with an expired notice. Old or stale cards are rejected or rerendered and never operate on a hidden, removed, or different project. Standalone model, progress, expired, result, and notification cards explicitly do not promote themselves to `lastCard`. The bottom menu has three keys: **主菜单** is the **escape hatch** — from any state it resets the session to idle and posts a **fresh** card at the bottom; **🤖 模型** posts the standalone two-level picker and **🛑 停止** cancels the caller's active child, health preflight, or accepted-before-spawn reservation, both **without touching the session**. Exact `event_id` + event age reject genuine Feishu redelivery; events without an id use only a 350ms message-scoped debounce so legal fast navigation is not swallowed.

The WS registration boundary uses `dispatchEvent` with a `setImmediate` boundary and a per-chat promise chain; registration therefore returns before both awaited I/O **and the handler's synchronous file-scan prefix**, while destructive operations finish before the next event in that chat begins. Feishu calls have bounded timeouts: normal send/patch requests use 7s, resource HTTP plus download-to-disk stages use 60s. Ambiguous timeouts are never retried; message creates carry a stable `uuid` so explicit retry after a recognized transient socket/TLS failure is idempotent, while uploads opt out of retry and destroy their source stream on timeout. Failed outbound images remain on disk at the reported path. **Results render as cards** (lark_md via `mdToLark` — headings→bold, bullets→•, code ticks stripped; plain text doesn't render markdown), with a plain-text fallback if the card send fails so an answer is never lost.

### Authorization (owner vs everyone-else)

`authLevel(openId)` → **full** (in `feishuAuthOpenIds`, or the list is empty = *not locked* = all full), else **viewer**. There is no per-user viewer grant: **everyone who isn't an owner is automatically a read-only viewer** (browse/query projects, never modify) — the intended model for opening the bot to coworkers. `canProject` = enter/query (always true once locked, viewers forced read-only); `canConfig` = full = modify / change config / authorize / browse work sessions. Chat is open to all (`authLevel` doesn't gate chat). `忘记查询` only clears the current user's own query memory and is available to both owners and viewers. Optionally promote someone with text `授权 ou_xxx` (or the one-tap owner card if it ever fires). Emptying `feishuAuthOpenIds` unlocks the bot for everyone — the GUI 授权用户 window and 取消授权 warn hard before that. The Feishu console never shows this roster; it lives in `config.json`, managed from the GUI 授权用户 window. (`feishuViewerOpenIds` is legacy/no-op now.)

In the migration worktree, D-003 additionally freezes one readable config snapshot at each message/card/menu entry. Authorization, menu/status/help rendering, project discovery, active-project resolution, enter/clear-query/stop routing and owner-notification-chat pre-admission consume that snapshot. `discoverProjects(cfg)` does not reread config and its three-second cache is separated by a `hiddenProjects`/`customProjects` fingerprint; `ConversationStore.activeProject(chatId, projects)` consumes the already-discovered list. A later disk change cannot upgrade a `none` event into project disclosure or an owner-chat binding, while a permitted config write still rereads and revalidates the latest config inside `config.json.write.lock` before atomic replacement. This hardening remains migration-only; Stage 6 must prove the equivalent target authorization path.

### The per-(project, user) query session

Each **(project, user, AI profile)** tuple has its own read-only Q&A session: follow-ups accumulate context, conversations stay **private**, and switching AI cannot inherit another provider's transcript. The isolated cwd and marker filename use `sha1(projectPath|open_id|profileId)`. Claude/DeepSeek derive a stable UUID and use `--session-id`/`--resume`; Codex records the native thread id returned by its first run and resumes it with `codex exec resume`. The first turn injects the project's `AI_GUIDE.md` (with a staleness note if its git marker is behind). Before any provider attempt, every existing project-path component is checked with `lstat`/`realpath`; symlink/junction/reparse or hard-linked guides are rejected, containment is proven, and content is read through the verified file handle. Unsafe or unverifiable guides fail locally before prompt construction. System temporary directories are excluded from production project discovery so provider smoke-test sessions cannot pollute the Feishu menu.

**Query tool lockdown (security).** `--permission-mode plan` blocks *writes* but **not reads**, and reads are not confined to the workspace — so an un-locked-down query could `Read ../../config.json` and exfiltrate secrets (verified live with benign phrasing; the model's refusal is not a boundary). Therefore only an **explicitly-listed owner** keeps file tools for queries (`--disallowedTools Task` only); **everyone else** — coworkers, and everyone while the bot is unlocked — runs with **no file/exec tools at all** and answers from the injected guide. Regression: `test/query-security.js`. Clearing a session goes through `session-manager.js`: Claude deletes the transcript + artifact directory, while Codex calls native `thread/delete` instead of merely dropping the marker.

### Prompt delivery, feedback, robustness

- **Prompt goes via STDIN, not `-p "<text>"`** — Windows `cmd` truncates a `-p` argument at the first newline, so a multi-line prompt lost everything after the framing (the long-standing "query fails" bug). `runClaude` writes the prompt to `child.stdin` then closes it (which also avoids claude's stdin-wait hang). Success is judged from the stream-json `result` line, never the exit code; stderr is captured for diagnostics; if there's no result but claude produced assistant text, that text is returned instead of a blank failure.
- **Progress = ONE standalone card, patched in place** (`startProgress`, ~20s ticks with elapsed time; a 15s-heartbeat *message* used to bury a 12-min run under ~48 lines). Tick/stop patches use their own per-run serial write chain and never enter or replace `lastCard`, so an older slow tick cannot overwrite the completion state, navigation cannot overwrite progress, and progress cannot overwrite navigation. If a tick itself times out, its uncancellable SDK request taints the old message; completion is then posted as a fresh lower card so that a late tick can only mutate the older card above it. On the normal path the original card becomes "✅ 已完成 · 用时 Ns" and the result follows as its own card ending with `⏱ Ns · 输出 N tokens · ≈ $X`.
- **Crash-safe runs**: every in-flight run is recorded in `feishu-inflight.json`; if the process dies mid-run (deploy/restart/crash), the next boot **tells the waiting user their run was cut off** — previously the run just vanished after the last heartbeat. Kills go through observable `killTree` (`taskkill /pid /t /f` — `child.kill()` can leave a wrapped Codex/Claude child running, verified). SIGINT/SIGTERM and process exit request termination of every registered AI child; redeploy via `install.ps1` targets only the runtime agent PID but kills its whole process tree before the VBS watchdog restarts it. Each spawned AI child is persisted with parent/child PID, `runKey`, task kind, start time, and provider using temp-file + fsync + replacement in `feishu-ai-children.json`. A first-write failure rejects the task and immediately requests termination; the in-memory run lock remains until real close/error while disk persistence retries. The migration worktree's D-001 stabilization (not yet deployed) classifies recovery as matched/mismatched/unverifiable: only a full parent/PID/start-time/provider-command match may be killed; missing or invalid metadata, CIM/monitor failure, unconfirmed kill, registry deletion/write failure, and entries without a valid PID retain the disk record plus runKey/legacy lock. Definite mismatch removes only the stale record and never kills the observed process. Stop/exit paths do not pass orphan placeholders to PID/tree termination. A complete temp/backup generation recovers a truncated main file. Stage 5 still replaces this Node registry with C# `ProcessSupervisor` + durable `RunStore` + Job Object.
- **Timeouts and persistence are task-scoped**: project modification, one-off execution and background auto-resume use zero as “no total-duration timer”; query/chat keep one shared 30-minute deadline. Feishu stop and GUI disarm are separate controls. The Scheduled Task is `PT0S`. Node and PowerShell acquire the same create-exclusive `config.json.write.lock`, then reread and mutate only owned fields before fsync + atomic replacement; a lock outside the read-modify-write transaction is insufficient because it can serialize a stale snapshot. Background state carries `armCycleId`/`cycleId`; `checker-ai-child.json` is written first as a launch intent and then as an active record, with complete temp/backup generations considered during recovery. Process probes return found/gone/failed; only explicit gone permits deletion. Missing start time, parent mismatch, command mismatch, CIM failure or unconfirmed `taskkill` keeps the registry fail-closed.
- **Images, both ways**: a caption-less inbound `image` is downloaded via `im.messageResource.get` (**`im:resource`** scope), parked by **chat + sender**, and folded into only that sender's next text message. A picture plus caption in one Feishu bubble is `message_type=post`: `parsePostContent` accepts both the production localized `{zh_cn:{title,content}}` envelope and a flat `{title,content}` body, selects the first locale with actual content, preserves paragraph text (including `at` fallback to `user_id`/`@all`), and de-duplicates embedded `img.image_key` values. The event downloads at most six resources in document order (10MB each), keeps them bound to that event, and claims them synchronously before background dispatch so later images cannot join the earlier request. The final merged turn is also capped at six; current post resources precede older parked images, overflow is deleted, and the user gets an explicit count. Busy/unsupported/blocked paths roll back those files; accepted runs keep them active until settlement and then delete them. Standalone orphan files and their in-memory queue entries become eligible after 24 hours and are swept hourly (worst case about 25 hours). Owner query/modify/chat paths accept local images; viewer query/chat runs have no file tools and delete/refuse images explicitly. Every message/card/menu event requires a currently readable valid config, a sender identity, and a successful optional allow-list check before any resource download or state transition; last-known-good config is retained only for non-entry fallback logic. Secondary partial-download/limit warnings are best-effort and cannot cancel the valid main request. Outbound: runs get an AppDir out-dir hint; files produced there are uploaded (`im.image.create` → **top-level** `{image_key}`, no `data` wrapper — a real shape trap) and sent after the run.
- Replies chunk to ≤6 parts. Single-instance via a pidfile + liveness check (Windows lets two sockets share a loopback port). Started at logon by a Startup-folder shortcut → `feishu-launch.vbs` (auto-restarts node, captures stdout). Logs use **local** time.
