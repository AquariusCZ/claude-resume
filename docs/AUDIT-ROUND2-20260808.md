## 0. 这一轮为什么换个组织方式

第一轮按"功能模块"分 T1–T7。但把今天一天找到的缺陷排开看,**它们是同一种形状**:

| 缺陷 | 界面当时显示 | 实际 |
|---|---|---|
| 钩子写成裸文件名 | 已启用 | 命令不在 PATH,永远不执行 |
| open_id 中间夹一个空格 | 进程在 / 平台 ready / API 200 | **每条飞书消息被静默丢弃** |
| notify 链套到 8 层 | 已启用 | 适配器早已拒绝处理 |
| 只读 five_hour/seven_day | 7 天 93%,正常,可运行 | Fable 已被拒 |
| 探测用随机临时 cwd | 自己的目录清得很干净 | 别人家里堆了 1135 条记录 |
| 计划任务默认设置 | daemon Running | 72 小时会被掐、拔电源就停、崩了不拉起 |
| cc-connect 的黑窗口 | ——(没有任何提示) | 关掉它 = 机器人下线且回不来 |

**七个缺陷,七次"界面说没事"。** 没有一个是崩溃,全部是**静默失败**。
崩溃至少会告诉你它崩了;静默失败要等到你发现"机器人怎么不理我"才暴露,
而那时距离根因已经隔了七层。

所以这一轮的主线不是"再测一遍功能",而是:

> **把界面上每一句肯定的话,追到它背后到底验证了什么。**

## 1. A 组 — 静默失败猎捕(最高价值)

对下面每一条界面文案,回答三个问题并给出证据:
**① 它凭什么这么说?② 那个依据能不能在"实际已坏"时仍然成立?③ 坏了的时候界面会变吗?**

| # | 界面文案 | 位置 | 已知风险 |
|---|---|---|---|
| A1 | 通知源开关「已启用」 | 右栏 NOTIFY | 探测只看配置里有没有我们的文件名。文件被删、路径被截断、链太深时呢? |
| A2 | 飞书「已配置 cli_xxx…」 | 右栏 FEISHU | 只证明 DPAPI 里有值。**app_secret 过期或被重置时,这里会变吗?** |
| A3 | 「cc-connect 配置已生成」 | fsNote | 只证明文件写成功。**写出去的内容 cc-connect 能不能加载?** |
| A4 | 状态灯「监视中」 | 顶部 beacon | 只读 config 的 Armed。**引擎进程真的在跑吗?Worker 被杀了这里会变吗?** |
| A5 | Agent「已记录」 | agentNote | 这条已经是诚实的(明说要重启才生效)。**核对它没有退化成"已生效"。** |
| A6 | Codex「可用 · 凭据已验证」 | 右栏 QUOTA | 1.3 秒的 /v1/models。**key 有权限列模型但没权限跑推理时呢?** |
| A7 | 队列里的项目路径 | 主列表 | 目录被删/改名后,这里还显示吗?布防它会怎样? |

**方法**:对每一条,人为制造"实际已坏"的状态(删文件、改权限、断网、改配置),
然后看界面**是否变化**。不变化的,就是下一个静默失败。

**这一组比 T1–T7 更该先做** —— 它找的是"还没被发现的那一类",而 T1–T7 找的是已知项。
